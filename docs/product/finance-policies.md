# 수익·정산의 계산과 기록 정책

2026-10-25 개발 중 스냅샷. 시작 기준 `dev` / `3576cbd92b0e02004be2cac179e41dca448c3ad5`.
현재 사용자 요구와 실제 코드가 바뀌면 API/DB 문서와 이 문서를 함께 갱신한다.
이 문서는 법적·회계적 적합성이나 운영 출시 승인을 의미하지 않는다.

## 금액과 근거

- 배치는 예정 정보다. 실제 `WORKED` 근태의 확인 상태를 정산 초안의 근거로 사용한다.
- `assignment.status`만으로 실제 근무를 추정하지 않는다. 일괄 예정 근무 후 해당 상태가 남는 기존 위험과 분리한다.
- 미입력 금액은 null이고 명시적 0원은 값이 존재하는 금액이다.
- 단가와 최종 금액, 농가 청구와 작업자 지급은 각각 독립적이다.
- 수량은 소수 3자리 이하, 단가×수량은 원 단위 HALF_UP 반올림을 사용한다. 최종 금액을 명시하면 그 금액을 우선한다.
- 조퇴/반일/휴게/연장은 표시하는 근태 근거이며 자동 비례 삭감의 입력값이 아니다.
- 기본값은 입력 보조다. 개별 수정된 행은 명시적인 덮어쓰기 확인 없이 기본값 재적용으로 바뀌지 않는다.
- 확정 시 당시 작업일·현장·거래처/작업자 표시명·지급 방식·금액을 스냅샷으로 보존한다.
- 확정 후 원천이 바뀌면 금액 재확인을 요구한다. 원천을 읽었다는 이유로 과거 금액을 다시 계산하지 않는다.

## 운영 방식과 작업이익

- `OFFICE`: 사무소 청구액 + 추가 항목 청구액 − 작업자에게 지급할 확정액 − 추가 항목 사무소 비용.
- `DIRECT`: 작업자 직접 지급분은 별도 확인 대상이며 사무소의 수납·출금·비용이 아니다.
  사무소가 받는 소개료를 청구액으로 입력하고 추가 청구액/비용으로 작업이익을 계산한다.
- 지급 처리 주체를 법적 고용주로 해석하지 않는다. 성별/배치 영역은 편의상 일괄 입력 필터이지 단가 강제 기준이 아니다.
- 참·식사·차량 등 비용은 추가 항목에서 한 번만 반영한다. 작업자 임금에서 자동 공제하지 않는다.
- 미수납/미지급 상태와 관계없이 확정 금액이 작업이익의 기준이다.
- 전체 고정비·세금·법정 수당이 포함된 순이익이나 회계 매출로 표시하지 않는다.

검산 기준:

| 사례 | 계산 | 작업이익 |
|---|---|---:|
| 사무소 수납·지급 | 150,000 + 10,000 − 130,000 − 5,000 | 25,000원 |
| 농가 직접 지급 | 소개료 20,000 + 10,000 − 5,000 (직접 지급 130,000 별도) | 25,000원 |
| 그룹 청구 | 8×140,000 + 2×160,000 | 청구 1,440,000원 |
| 부분 주급 지급 | 지급할 650,000 − 실제 지급 300,000 | 미지급 350,000원 |

## 날짜와 집계

- 업무 날짜 기준은 Asia/Seoul이다. 수익 현황은 작업일, 실제 입출금은 기록한 입출금일로 조회한다.
- 전체 미수·미지급 목록은 수익 조회 기간과 무관하게 과거 잔액도 포함한다.
- 수납/지급 예정일 null은 미정이고 기한 경과가 아니다. 기한 경과는 잔액 상태와 별도로 표시한다.
- 당일/주 단위/날짜 지정은 지급 편의 설정이다. 주 단위의 월~일 작업분은 다음 주에 선택한 요일에 지급하는 방식이다.
- 설정 변경은 이미 저장된 과거 예정일을 일괄 변경하지 않는다. 과거 변경은 사유와 원래 값을 보존한다.
- 2026-10-26 사용자 승인: 작업별 현금/송금 및 당일/7일 뒤/수금 후/직접 날짜를 지급 예정 정보로 기록한다. 7일 뒤는 작업일+7일이며 주급의 특정 요일과 다르다.
- 수금 후 지급 선택은 예정 의향 표시다. 실제 수금 완료 여부를 추정하지 않으며 지급을 막거나 기존 예정일을 자동 연기하지 않는다. 예정 수단과 실제 지급 기록의 수단은 각각 보존한다.
- 같은 사람이 하루 여러 현장에서 일하면 현장별 투입은 여러 건이다. 고유 작업자 수와 혼합해서 표시하지 않는다.
- 익명 배정 UUID가 다르면 같은 사람인지 알 수 없다. 이를 고유 인원으로 추정하지 않는다.

## 수납·지급과 정정

- 청구·지급 의무와 실제 입출금 기록, 내역별 배분을 분리한다.
- 농가 수납은 작업자 지급을 완료하지 않고, 농가 미입금은 작업자 지급을 막거나 예정일을 연장하지 않는다.
- 농가 직접 지급도 별도 확인 기록이 있어야 완료로 표시한다.
- 배분 합계는 기록 금액과 일치해야 하며 같은 사무소·수단 종류·상대방의 잔액 안에서만 배분한다.
- 초과입금, 선급금, 미배분 잔액은 이번 버전의 입력 대상이 아니다. 명시적으로 거부한다.
- UUID 요청 식별자, 서버 트랜잭션과 사무소 범위 직렬화로 중복 요청/동시 배분을 검증한다.
- 취소/정정은 원본을 삭제하거나 덮어쓰지 않는다. 원본, 취소 사유, 처리자·시각, 대체 기록의 연결을 보존한다.
- 확정액이 줄어 이미 수납/지급한 금액이 더 크면 음수 잔액을 숨기지 않고 정정 확인 대상으로 표시한다.
- 실제 송금, 자동 입금 확인, 세금·법정 급여 계산은 하지 않는다.

## 출시 차단과 결정 대기

- 현재 `loginId → ACTIVE 계정 → 사무소` 검사는 실제 인증·권한 검증이 아니다.
  다른 loginId의 사칭을 막는 인증/역할 인가가 없으므로 외부 운영·금전정보 공개 전 출시 차단 사항이다.
- 과거 `worker_count > 1` 묶음 배정은 개인별 근태와 수령자를 확정할 수 없다.
  2026-10-25 사용자 승인에 따라 개인별 분리·근태 확인 전 금액 확정을 차단한다.
  배정 인원을 실제 인원으로 추정하거나 묶음 금액을 임의로 확정하지 않는다.
- 실제 법적 지급 의무·주기 적합성은 이 소프트웨어가 판단하거나 보장하지 않는다.

## 사용 확인 순서

1. 근태에서 실제 근무를 확인하고 해당 작업의 금액 화면으로 이동한다.
2. 작업 금액 화면에서 청구/지급 금액을 바로 수정하고 저장한다. 별도 초안 생성 조작은 없다. 작업자 예외와 추가 항목, 예정일을 확인한 뒤 금액을 확정한다.
   작업 팝업의 농가 청구/작업자 지급을 구분해 입력한다. 추가 청구가 지급액에 자동 가산되지는 않는다. 같은 이름은 인접 정렬만 하고 익명 인원/배정을 합치지 않는다.
3. 농가 수납에서 일부 금액 또는 여러 작업의 배분안을 확인하고 수납 사실을 기록한다.
4. 작업자 지급에서 수납과 무관하게 실제 지급 사실을 기록한다. 직접 지급은 확인 필요/확인 완료를 구분한다.
5. 전체 잔액에서 이전 달 기록, 기한 경과, 예정일 미정을 각각 확인한다.
6. 잘못된 기록을 사유와 함께 정정하고 원본 이력·잔액 복원을 확인한다.
7. 확정 후 근태를 바꿨을 때 금액이 자동 변경되지 않고 재확인 표시가 나오는지 확인한다.

## 실행 검증과 남은 범위

- 2026-10-25 지정 core 검증을 임시 PostgreSQL 18에서 실행: 145개 통과, 실패·건너뜀 0.
  정산 관련 69개(HTTP 7, 계산 11, 서비스 27, 실제 JDBC 24)를 포함한다.
- 실제 JDBC 검증에는 부분·일괄 배분, 월말을 넘는 주급, 동시 요청과 재시도, 타 사무소 대상 거부,
  취소·정정 롤백, 확정 표시명 보존, 전액 정산 후 조회, DB 배분·삭제 보호 제약을 포함한다.
- web 검증: 기존 38개와 정산 26개 통과, TypeScript·Vite 빌드 통과. 500kB 초과 번들 경고는 남아 있다.
- 재현: `.skills/verify-finance.ps1`(또는 `.sh`)과 `.skills/verify-web.ps1`.
  finance 검증은 로컬에 `postgres:18` 이미지가 있어야 하며 원격 고객 DB는 사용하지 않는다.
- 고객 DB에는 036을 적용하지 않았다. 최소 부모 스키마+036만 검증했으며,
  전체 001~036 이행, 운영 데이터 업그레이드, 실제 인증·역할 인가 검증을 완료한 것은 아니다.
- 브라우저 화면 검증은 모의 fetch/가상 데이터로 PC 1366×900, 모바일 크기 390×844에서 수행했다.
  탭 전환, 부분 지급·취소, 전액 지급 후 기록 표시명·현장, 정정 화면, 직접 지급 문구와 가로 넘침을 확인했다.
  이는 브라우저 크기 조정 검증이다. 실제 API·DB를 연결한 브라우저 재접속,
  실제 휴대폰의 키보드·터치와 장시간/대량 데이터 성능은 별도 확인 대상이다.
- 이미 확정한 지급 대상의 식별자 변경(익명→등록 포함)은 원장을 자동 이관하지 않고 거부한다.
  기존 원장·현금 기록을 보존하면서 개별 배정/근태를 다시 확인하는 운영 절차가 필요하다.
